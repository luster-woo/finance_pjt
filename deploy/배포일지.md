# 배포일지 — FinFit

## 기본 정보

- 배포일: 2026-09-12
- 서버: AWS EC2 t3.small (2 vCPU / 1.9GiB), Ubuntu 24.04.4 LTS, x86_64, 서울 리전
- 구성: nginx(리버스 프록시) · Django 5.2 + gunicorn(워커 3) · PostgreSQL 16 · APScheduler 전용 컨테이너
- 총 소요 시간: 약 2시간 (로컬 리허설 포함)

배포 절차 자체는 `README.md` 에 있다. 여기에는 실제로 막힌 것만 적는다.

## 0. 먼저 로컬에서 운영 구성을 띄웠다

서버로 가기 전에 `docker-compose.prod.yml` 을 로컬 Docker 에서 그대로 한 번 기동했다.
결과적으로 이 판단이 가장 크게 작용했다. **서버에서 겪은 문제 네 건이 전부 인프라
문제였고, 애플리케이션 레벨 문제는 한 건도 없었다.**

로컬 리허설에서 미리 통과시킨 것들:

- `migrate` 전체 적용, `collectstatic` 154개 파일
- SPA 진입 HTML 이 `/assets/index-BpvkiKrK.js` 를 참조 — `FE/public/index.html` 잔재 없음
- `/api/products/` 200 — nginx `proxy_pass` 끝 슬래시 정상
- `/static/admin/css/base.css` 200 — 정적 파일 볼륨 공유 정상
- `sched` 컨테이너 로그에 `[scheduler] APScheduler 시작`
- `DEBUG=False` 상태에서 400 이 나지 않음

이 목록은 원래 "배포하면 터질 것 같은 것"으로 예상했던 항목들이다. 서버에서 첫 빌드가
10분 걸리는 걸 감안하면, 이걸 로컬에서 먼저 걸러낸 것과 아닌 것의 차이는 컸을 것이다.

## 기록

### #1 — 인스턴스 시작이 거부됨 (10분)

- **증상**: 인스턴스 시작을 눌렀는데 실패.
  `Microsoft SQL Server is not supported for the instance type 't3.small'.`
- **처음 생각한 것**: 메시지가 인스턴스 유형을 지목하니 t3.small 이 문제인 줄 알았다.
  더 큰 유형으로 바꾸려다 멈췄다. 서버 사양과 SQL Server 가 무슨 상관인가 싶어서였다.
- **원인**: AMI 가 `Ubuntu Server 22.04 LTS (HVM) with SQL Server 2022 Standard` 였다.
  목록 상단에서 `Ubuntu` 타일을 눌렀지만, **타일은 OS 계열 필터일 뿐이고 실제 선택은 그
  아래 드롭다운**이다. 드롭다운 기본값이 SQL Server 라이선스가 포함된 유료 이미지였다.
- **조치**: 드롭다운을 열어 `Ubuntu Server 24.04 LTS (HVM), SSD Volume Type` 으로 변경.
- **알게 된 것**: 에러 메시지가 지목하는 대상이 원인이 아닐 수 있다. 여기서는 유형이
  문제가 아니라 **이미지와 유형의 조합**이 문제였고, 메시지는 그중 뒤쪽만 말하고 있었다.
  "SQL Server 를 고른 적이 없는데 왜 이 메시지가 나오지"에서 출발한 게 맞았다.
  선택하지 않은 것이 메시지에 등장하면, 내가 선택했다고 믿은 것부터 다시 본다.

### #2 — 빌드가 `no space left on device` 로 실패 (25분)

- **증상**: `docker compose up --build` 중 이미지 레이어 압축 해제 단계에서 실패.
  ```
  failed to extract layer ... write /var/lib/containerd/.../libLLVM.so.21.1:
  no space left on device
  ```
- **원인**: `df -h /` 를 보니 `6.8G 중 6.5G 사용, 여유 212M`. EBS 를 20GiB 로 설정했다고
  생각했는데 실제로는 기본값 8GiB 로 생성돼 있었다. 거기에 **직전 단계에서 만든 4GB
  스왑파일이 디스크를 그대로 차지**하고 있었다. 도커 이미지 네 개를 빌드하려면
  5~6GB 가 필요한데 시작도 못 한 것이다.
- **조치**: 콘솔에서 볼륨을 20GiB 로 수정한 뒤, 서버에서 파티션과 파일시스템을 따로 확장.
  ```
  sudo growpart /dev/nvme0n1 1     # 7G -> 19G
  sudo resize2fs /dev/nvme0n1p1
  ```
  결과: `19G 중 6.5G 사용, 여유 12G`. 재빌드 성공.
- **알게 된 것**: 두 가지다.
  첫째, **스왑은 메모리 대책이지만 실체는 디스크 위의 파일이다.** OOM 을 막으려고 만든
  것이 디스크를 절반 먹어 다른 실패를 만들었다. 자원 하나를 늘리는 조치가 다른 자원을
  줄인다는 걸 놓쳤다.
  둘째, **볼륨을 키워도 OS 는 모른다.** AWS 가 디스크를 20GiB 로 바꿔줘도 리눅스는
  파티션 테이블에 적힌 예전 크기를 그대로 믿는다. `lsblk` 에는 `nvme0n1 20G` 로 보이는데
  `nvme0n1p1` 은 여전히 7G 인 상태가 그래서 나온다. 클라우드 층과 OS 층이 각자 따로
  알고 있고, 그 사이를 `growpart` 와 `resize2fs` 가 잇는다.

### #3 — 서버 안에서 `/api/*` 가 400 (10분)

- **증상**: 빌드 성공 후 서버 안에서 확인하는데 응답이 갈렸다.
  ```
  /                            -> 200
  /static/admin/css/base.css   -> 200
  /api/products/               -> 400
  /admin/                      -> 400
  ```
- **원인**: `ALLOWED_HOSTS=32.196.241.19` 만 넣어둔 상태에서 `curl http://localhost/...`
  로 찔렀다. Host 헤더가 `localhost` 로 가니 Django 가 거부한 것이다.
- **조치**: `curl -H "Host: 32.196.241.19" http://localhost/api/products/` 로 재확인 →
  200. 설정 문제가 아니라 테스트 방법 문제였다.
- **알게 된 것**: **200 과 400 이 갈린 지점 자체가 정보였다.** `/` 와 `/static/` 은
  nginx 가 직접 서빙하니 Host 검사를 거치지 않고, `/api/` 와 `/admin/` 만 Django 로
  넘어가서 검사를 받는다. 즉 "어떤 경로가 실패하는가"가 곧 "어느 구성요소가 관여하는가"를
  알려준다. 전부 400 이었다면 nginx 문제였을 것이고, 전부 200 이었다면 넘어갔을 것이다.

### #4 — 컨테이너는 다 떴는데 바깥에서 안 열림 (20분 — 가장 오래 막힘)

- **증상**: `docker compose ps` 는 네 개 전부 Up, 서버 안에서는 200. 그런데 내 PC 에서
  `http://32.196.241.19` 가 15초 타임아웃. 응답 코드조차 안 나왔다(`000`).
- **좁혀간 순서**: 가장 안쪽부터 한 겹씩 벗겨 나갔다.
  1. 서버 안에서 `curl -I http://localhost` → **200**
     → 애플리케이션·nginx·도커 네트워크는 전부 정상. 문제는 서버 바깥 경계에 있다.
  2. `sudo ss -tlnp | grep :80` → **`0.0.0.0:80` LISTEN (docker-proxy)**
     → 특정 인터페이스에만 바인딩된 게 아니다. 포트는 열려 있다.
  3. `sudo ufw status` → **inactive**, `sudo iptables -L INPUT -n` → **policy ACCEPT, 규칙 없음**
     → OS 방화벽도 아니다. 남은 건 서버 밖이다.
  4. 서버 안에서 **자기 자신의 퍼블릭 IP** 로 `curl` → **타임아웃**
     → 루프백은 되는데 공인 IP 로는 나가지도 들어오지도 못한다. **여기가 결정타였다.**
     막는 주체가 인스턴스 안이 아니라 VPC 경계라는 게 이 한 줄로 확정됐다.
  5. 메타데이터(`169.254.169.254`)로 인스턴스가 인식하는 퍼블릭 IP 확인 → 주소도 맞았다.
- **원인**: 보안 그룹 `launch-wizard-1` 의 인바운드에 SSH(22) 만 있고 **HTTP(80) 규칙이
  없었다.** 인스턴스 생성 마법사에서 설정한 것이 SSH 에만 적용됐다.
- **조치**: 보안 그룹 > 인바운드 규칙 편집 > HTTP / 0.0.0.0/0 추가. 저장 즉시 반영됐고
  재시작은 필요 없었다. 바로 다시 확인하니 전부 200.
- **알게 된 것**: "서버가 떴다"와 "밖에서 닿는다"는 완전히 다른 문제다. 경계가 여러 겹일 때는
  **가장 안쪽(localhost)부터 확인해서 바깥으로 나간다.** 안쪽이 200 이면 그 구간 전체가
  용의선상에서 지워지고 범위가 절반씩 줄어든다.
  4단계의 "서버가 자기 공인 IP 를 호출한다"가 특히 유용했다. 루프백과 공인 IP 를 갈라
  **경로가 VPC 를 한 번 나갔다 들어오는지**를 단독으로 시험할 수 있었다.
  EC2 는 보안 그룹 한 겹이라 여기서 끝났지만, OS 방화벽까지 쓰는 환경이라면 3단계에서
  걸렸을 것이다. 순서를 지키면 어느 환경이든 같은 방식으로 좁혀진다.

## 검증 결과

바깥에서 최종 확인한 응답이다.

| 경로 | 응답 | 응답시간 |
|---|---|---|
| `/` | 200 | 0.38s |
| `/api/products/` | 200 | 0.40s |
| `/api/news/` | 200 | 0.42s |
| `/admin/` | 302 | 0.42s |
| `/static/admin/css/base.css` | 200 | 0.59s |
| `/products/1` (SPA 폴백) | 200 | 0.40s |

admin 은 로그인까지 확인했다. CSRF 토큰을 받아 POST 하니 302 와 함께 `sessionid` 쿠키가
내려왔고, 그 쿠키로 `/admin/` 이 200 (`사이트 관리 | Django 사이트 관리`)을 반환했다.
`CSRF_TRUSTED_ORIGINS` 에 스킴을 포함해 넣어둔 것이 맞게 동작했다.

실측 리소스:

| 컨테이너 | 메모리 |
|---|---|
| web (gunicorn 워커 3) | 305MB |
| sched (APScheduler) | 102MB |
| db (PostgreSQL 16) | 58MB |
| nginx | 4MB |
| **합계** | **469MB** |

디스크는 이미지 포함 8.5GB. 이 수치를 보면 1GiB 인스턴스에서도 **구동은** 가능하지만,
빌드 단계의 `npm run build` 때문에 스왑 없이는 어렵다.

## 배포 전후로 바뀐 것

배포를 하려면 코드를 고쳐야 했던 지점들. 이게 "환경 분리를 해봤다"의 실제 내용이다.

| 항목 | 개발 | 운영 | 왜 달라야 했나 |
|---|---|---|---|
| DB | SQLite 파일 | PostgreSQL 컨테이너 | 컨테이너를 다시 만들면 파일 DB는 날아간다. 데이터와 실행환경의 수명이 달라야 재배포가 안전해진다 |
| 정적 파일 | Django가 직접 서빙 | collectstatic → nginx가 서빙 | `DEBUG=False` 면 Django는 정적 파일을 서빙하지 않는다 |
| 스케줄러 | runserver 프로세스 안 | 전용 컨테이너 1개 | 웹 워커는 3개, 주기 작업은 1개여야 한다 |
| 비밀값 | `.env` | 서버의 `.env.prod` (git 제외) | 이미지에 굽지 않고 실행 시점에 주입 |
| CORS | 전체 허용 | 불필요 | nginx가 FE와 API를 한 오리진으로 묶었다 |
| 프론트 API 주소 | `http://127.0.0.1:8000` | `/api` (상대 경로) | 도메인이 바뀌어도 프론트를 다시 빌드하지 않아도 된다 |

스케줄러 분리는 배포를 준비하면서 미리 고친 부분이다. 원래 `config/apps.py` 가
`RUN_MAIN` 환경변수로 중복 실행을 막고 있었는데, 이건 runserver 의 리로더가 설정하는
변수라 **gunicorn 에는 아예 존재하지 않는다.** 그대로 뒀다면 배포하는 순간 스케줄러가
조용히 꺼졌을 것이다. 그렇다고 web 컨테이너에서 켜면 gunicorn 워커 3개가 같은 뉴스 수집을
3번 돌린다. 웹 서버는 여러 개로 늘리는 게 정상이고 주기 작업은 하나만 돌아야 하니,
수명 주기가 다른 둘을 프로세스로 분리했다.

## 다시 한다면

- **EBS 는 처음부터 20GiB 로.** 8GiB 는 스왑을 쓰는 순간 부족하다. 볼륨은 늘릴 수는 있어도
  줄일 수 없으니 처음에 넉넉히 잡는 게 맞다.
- **보안 그룹 인바운드는 인스턴스 생성 직후 바로 확인.** 마법사에서 설정했다고 믿지 않는다.
- **로컬 리허설은 다음에도 먼저 한다.** 이번에 앱 레벨 문제가 0건이었던 게 우연이 아니다.
- HTTPS 는 붙이지 않았다. 도메인 없이 IP 로만 띄웠기 때문이다. 실제 서비스라면
  도메인 + Let's Encrypt 까지 가야 한다.

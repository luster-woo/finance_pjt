## 기록

### #1 — `docker: permission denied` (예상 · 10분)

- **증상**: `sudo usermod -aG docker $USER` 를 실행했는데도 `docker ps` 가
  `permission denied while trying to connect to the Docker daemon socket` 를 냄.
- **원인**: 리눅스 그룹 정보는 **로그인 시점에 결정된다.** 이미 열려 있는 SSH 세션에는
  방금 추가한 docker 그룹이 반영되지 않는다.
- **조치**: `exit` 후 재접속. `groups` 로 docker 포함 확인.
- **알게 된 것**: `usermod` 는 파일(`/etc/group`)을 바꿀 뿐, 실행 중인 프로세스의
  권한을 바꾸지 못한다. 프로세스는 시작할 때 받은 자격증명을 그대로 들고 산다.

### #2 — `npm run build` 가 메시지 없이 죽음 (예상 · 40분)

- **증상**: `docker compose up --build` 중 프론트 빌드 단계에서 컨테이너가
  `exit code 137` 로 종료. 에러 로그는 없음.
- **원인**: 메모리 부족(OOM). 137 = 128 + 9 (SIGKILL), 즉 **커널이 죽인 것**이지
  애플리케이션이 실패한 게 아니다. 로그가 없는 이유도 그래서다.
- **조치**: `dmesg | grep -i "killed process"` 로 OOM Killer 기록 확인 →
  4GB 스왑 생성 후 재빌드.
- **알게 된 것**: exit code가 128을 넘으면 시그널로 죽은 것이다(코드 − 128 = 시그널 번호).
  애플리케이션 로그를 아무리 뒤져도 안 나오는 종류의 실패가 있고,
  그때는 컨테이너 밖(`dmesg`, `docker inspect`)을 봐야 한다.

### #3 — 컨테이너는 다 떴는데 브라우저가 안 열림 (예상 · 1시간 30분 — 가장 오래 막힘)

- **증상**: `docker compose ps` 는 전부 Up. `docker logs nginx` 도 정상.
  그런데 `http://<공인IP>` 가 무한 로딩 후 타임아웃.
- **원인**: Oracle Cloud는 방화벽이 **두 겹**이다.
  (1) 콘솔의 Security List, (2) 인스턴스 내부 iptables.
  Ubuntu 이미지는 기본으로 80을 DROP 한다. Security List만 열고 끝낸 상태였다.
- **좁혀간 순서**: 바깥에서 안으로 한 겹씩 벗겼다.
  1. 서버 **안에서** `curl -I http://localhost` → **200 OK**
     → 애플리케이션·nginx·도커 네트워크는 전부 정상. 문제는 서버 바깥 경계에 있다.
  2. 서버 안에서 `curl -I http://<공인IP>` → 타임아웃
     → 루프백은 되는데 공인 IP는 안 된다 = 네트워크 계층에서 막히는 중.
  3. `sudo iptables -L INPUT -n --line-numbers` → 80 ACCEPT 규칙 없음. **여기였다.**
- **조치**:
  ```
  sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
  sudo netfilter-persistent save
  ```
- **알게 된 것**: "서버가 떴다"와 "밖에서 닿는다"는 완전히 다른 문제다.
  경계가 여러 겹일 때는 **가장 안쪽(localhost)부터 확인해서 바깥으로 나간다.**
  안쪽이 200이면 그 뒤는 전부 용의선상에서 지워지고 범위가 절반씩 줄어든다.
  `netfilter-persistent save` 를 빼먹으면 재부팅 때 되살아난다 —
  다음날 똑같은 증상을 다시 만나고 나서야 이걸 알았다.

### #4 — 사이트가 백지, 콘솔에 `/src/main.js` 404 (예상 · 30분)

- **증상**: nginx는 200을 반환하는데 화면이 비어 있음.
  브라우저 콘솔: `GET /src/main.js net::ERR_ABORTED 404`.
- **원인**: `FE/public/index.html` 에 Vite 초기 세팅 때의 진입 HTML이 남아 있었다.
  Vite는 `public/` 의 파일을 `dist/` 루트로 **그대로 복사**하므로,
  빌드가 만든 진짜 `index.html`(해시 붙은 `/assets/*.js` 참조)을 덮어썼다.
- **조치**: `git rm FE/public/index.html` 후 재빌드.
  Dockerfile에 `test -f dist/index.html && grep -q '/assets/' dist/index.html` 검증 추가.
- **알게 된 것**: **로컬에서 절대 재현되지 않는 버그가 있다.**
  dev 서버는 루트 `index.html` 을 쓰고 `public/` 을 거치지 않기 때문이다.
  `npm run dev` 가 잘 된다는 건 `npm run build` 가 잘 된다는 뜻이 아니다.
  배포 전에 로컬에서 한 번은 `build` + `preview` 를 돌려봐야 한다.

### #5 — `Bad Request (400)` (예상 · 15분)

- **증상**: 브라우저에 Django의 흰 화면 400. `docker logs web` 에
  `Invalid HTTP_HOST header: '<IP>'. You may need to add '<IP>' to ALLOWED_HOSTS.`
- **원인**: `.env.prod` 의 `ALLOWED_HOSTS` 를 비워둔 채 배포.
  `DEBUG=False` 가 되는 순간 Django는 Host 헤더를 검사한다.
- **조치**: `ALLOWED_HOSTS=<IP>` 추가 → `up -d`.
- **알게 된 것**: `DEBUG=False` 는 단순히 에러 페이지만 바꾸는 스위치가 아니다.
  ALLOWED_HOSTS 검사가 켜지고, 정적 파일 서빙이 꺼지고, 쿠키 보안 옵션이 달라진다.
  개발과 운영이 갈라지는 지점이 이 플래그 하나에 몰려 있다.

### #6 — API 요청이 전부 404 (예상 · 25분)

- **증상**: 화면은 뜨는데 모든 API가 404. `docker logs web` 에는
  `"GET /api/products/ HTTP/1.0" 404`.
- **원인**: nginx `proxy_pass http://backend;` — **끝 슬래시를 빠뜨렸다.**
  슬래시가 없으면 원래 경로가 그대로 전달돼 Django가 `/api/products/` 를 받는데,
  `config/urls.py` 에는 `/api` 접두사가 없다.
- **조치**: `proxy_pass http://backend/;` 로 수정.
- **알게 된 것**: `proxy_pass` 의 끝 슬래시는 **location 접두사를 떼느냐 마느냐**를 결정한다.
  로그에서 `web` 이 받은 경로를 직접 보는 게 제일 빠른 확인법이었다.
  nginx 로그(`/api/products/` 200)와 Django 로그(`/api/products/` 404)를 나란히 놓으면
  어느 구간에서 경로가 안 바뀌었는지 바로 보인다.

### #7 — admin 화면 CSS가 전부 깨짐 (예상 · 20분)

- **증상**: `/admin/` 이 열리긴 하는데 스타일이 하나도 없음. `/static/admin/css/base.css` 404.
- **원인**: `DEBUG=False` 에서 Django는 정적 파일을 서빙하지 않는다.
  `collectstatic` 결과물을 nginx가 읽도록 볼륨을 공유해야 하는데,
  `STATIC_ROOT` 와 nginx `alias` 경로가 어긋나 있었다.
- **조치**: `docker exec web ls /app/staticfiles` 로 파일 존재 확인 →
  `docker exec nginx ls /vol/static` 으로 볼륨이 실제로 보이는지 확인 → 경로 정렬.
- **알게 된 것**: 컨테이너 간 파일 공유 문제는 **양쪽에서 각각 `ls` 를 해보면 5초 만에 끝난다.**
  "설정이 맞겠지"라고 믿고 설정 파일만 노려보는 것보다, 실제 파일 시스템을 보는 게 빠르다.

### #8 — 뉴스·시세가 갱신되지 않음 (예상 · 40분)

- **증상**: 배포 후 하루가 지나도 뉴스가 그대로. `docker logs web` 에
  `[scheduler]` 로그가 **한 줄도** 없음.
- **원인**: `config/apps.py` 가 `if os.environ.get('RUN_MAIN') != 'true': return` 였다.
  `RUN_MAIN` 은 runserver의 리로더가 설정하는 변수라 **gunicorn에는 아예 존재하지 않는다.**
  즉 배포하는 순간 스케줄러는 무조건 꺼졌다. 로컬에서는 멀쩡히 돌아서 몰랐다.
- **조치**: 조건을 `RUN_SCHEDULER` 환경변수로 분리하고,
  스케줄러를 `manage.py run_scheduler` 를 실행하는 **전용 컨테이너**로 떼어냈다.
- **알게 된 것**: 처음엔 web 컨테이너에서 그냥 켜려 했는데, gunicorn 워커가 3개라
  같은 뉴스 수집이 3번 동시에 돌 상황이었다. **웹 서버는 여러 개로 늘리는 게 정상이고,
  주기 작업은 하나만 돌아야 한다** — 이 둘은 애초에 수명 주기가 다르니 프로세스를 분리한다.
  "로컬에서 잘 되는데 배포하면 안 되는" 문제의 원인이 보통 이런
  **개발 서버에만 있는 전제**에 있다는 것도 같이 배웠다.

## 배포 전후로 바뀐 것

배포를 하려면 코드를 고쳐야 했던 지점들. 이게 "환경 분리를 해봤다"의 실제 내용이다.

| 항목 | 개발 | 운영 | 왜 달라야 했나 |
|---|---|---|---|
| DB | SQLite 파일 | PostgreSQL 컨테이너 | 컨테이너를 다시 만들면 파일 DB는 날아간다. 데이터와 실행환경의 수명이 달라야 재배포가 안전해진다 |
| 정적 파일 | Django가 직접 서빙 | collectstatic → nginx가 서빙 | `DEBUG=False` 면 Django는 정적 파일을 서빙하지 않는다 |
| 스케줄러 | runserver 프로세스 안 | 전용 컨테이너 1개 | 웹 워커는 3개, 주기 작업은 1개여야 한다 (#8) |
| 비밀값 | `.env` | 서버의 `.env.prod` (git 제외) | 이미지에 굽지 않고 실행 시점에 주입 |
| CORS | 전체 허용 | 불필요 | nginx가 FE와 API를 한 오리진으로 묶었다 |
| 프론트 API 주소 | `http://127.0.0.1:8000` | `/api` (상대 경로) | 도메인이 바뀌어도 프론트를 다시 빌드하지 않아도 된다 |

## 스스로 확인할 질문 (면접에서 그대로 나온다)

각 항목에 **한 문장씩** 답을 적어둔다. 못 적으면 아직 이해한 게 아니다.

- [ ] gunicorn과 nginx는 각각 무슨 일을 하나. 왜 둘 다 필요한가
- [ ] gunicorn 워커 수를 3으로 잡은 근거는
- [ ] DB 포트를 외부에 열지 않은 이유는
- [ ] `DEBUG=False` 로 바꾸면 무엇이 달라지나 (→ #5)
- [ ] 컨테이너를 다시 올려도 데이터가 남는 이유는 (볼륨)
- [ ] 재배포할 때 마이그레이션은 어느 시점에 도는가
- [ ] 스케줄러를 웹 서버와 분리한 이유는 (→ #8)
- [ ] **배포 중 가장 오래 막힌 문제 하나와, 그걸 어떻게 좁혀 들어갔나** (→ #3)

마지막 질문이 제일 중요하다. 정답을 알고 있었는지가 아니라
**원인을 어떻게 좁혔는지**를 묻는 것이다.
#3처럼 `curl localhost` → `curl 공인IP` → `iptables -L` 로
**바깥에서 안으로 한 겹씩 벗겨간 순서**를 말하면 된다.
